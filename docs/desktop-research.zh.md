# 桌面端技术调研

> 状态：尚未选型。本文记录待验证的问题，不代表已经确定桌面端方案。

SeatTrellis 目前提供 CLI 和本地 Streamlit 页面。桌面版的主要价值是省去
Python 环境配置，并提供文件选择、最近项目和手动调整座位等更自然的操作。
核心排座逻辑仍应保留在 Python 包中。

## 约束

- Windows、macOS 和 Linux 都要能构建；
- 学生数据只在本机处理；
- 安装包应包含运行所需的 Python 环境；
- UI 通过 service API 调用核心逻辑，不另写一套规则；
- 首个原型不做账号、云同步、自动更新或本地数据库。

## 候选方案

| 方案 | 好处 | 主要问题 |
|------|------|----------|
| Tauri + Python sidecar | 原生窗口，前端布局自由，壳本身较小 | Python 运行时打包和进程通信较复杂 |
| PySide/PyQt | 可直接调用 Python 代码，调试路径短 | Qt 依赖较大，需要核对许可证和打包流程 |
| FastAPI + pywebview | Web 前端与 Python 服务边界清楚 | 需要维护本地服务生命周期和前端资源 |
| NiceGUI | 主要使用 Python，原型速度快 | 桌面打包经验和长期维护成本还需验证 |
| Electron | 工具链成熟 | 安装包通常较大，而且仍需处理 Python sidecar |

表中的体积和启动速度不能只凭框架宣传判断，必须用同一个最小功能原型测量。

## 建议的验证方式

先做两个一次性原型：

1. PySide：打开一个 project，调用 `compute_solve`，展示座位表；
2. Tauri：启动 Python sidecar，完成同一条工作流。

每个原型记录以下数据：

- 干净机器上的安装步骤；
- 安装包大小和首次启动时间；
- 中文字体、PDF 预览和文件选择是否正常；
- Python 异常如何传到界面；
- Windows 和 macOS 的签名、公证与 CI 配置量；
- 关闭窗口后是否还有残留进程或临时文件。

如果 Tauri sidecar 在打包和错误处理上没有明显障碍，再考虑把它作为桌面端
主方案；否则优先使用 PySide，减少跨进程接口。FastAPI + pywebview 可作为
第三个对照，不需要同时维护三个长期分支。

## 暂缓事项

自动更新、SQLite、插件系统和前端框架选型都等原型结论后再讨论。当前工作
仍以 CLI、Web 和 service API 的稳定性为主。
