# SeatTrellis v2 M4 — Product Decision Record · Batch 1（核心工作流 D1–D8）

> 批次：批 1 核心工作流（修订版计划 §7.1 项 1–8）
> 日期：2026-08-10
> 流程：计划 §0.5 Decision Gate——原型展示（`docs/prototypes/`，真实 parity corpus 数据）→ 逐项选择/融合反馈 → 本记录冻结
> 决策人：产品负责人（用户）
> 状态：**已决策，冻结交互契约草案；待目标形态页确认与 dogfood 验证后进入实现**

## 全局决策（适用于本批全部条目）

- **G-1 通俗化文案资产**：面向教师的展示不得使用程序内部术语（如 `fair_rotation`、`hard_constraint_summary`）。术语映射表见 D5。通俗文案以 i18n `message_key + args` 资产承载（与 Rust audit `suggested_actions` 结构一致），禁止 UI 硬编码。
- **G-2 视图同步架构约束**：任何"同一编辑状态多视图"（画布/表格、列表/画布、候选多视图）必须共享同一编辑状态与 undo/redo 栈，所有持久操作走 Rust editing 协议命令并经独立 validator 复核。违反即偏离计划（§0.3/§4.2）。
- **G-3 复现性不因通俗化隐藏**：seed / solver / build / 规则版本 / history range / candidate id 必须可查（§7.6），统一收进"详情"折叠区并在导出元数据中携带。
- **G-4 默认值证据要求**：候选数、历史期数、默认视图等默认值，须经原型真实任务测试后冻结，不得在实现阶段随意修改。
- **G-5 临时工作台语义**（计划 §7.4）：一次性排座 = 未保存的临时上下文；保存后自然升级为正式班级，不构成第二个产品概念。

## D1 班级主导航

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D1-NAVIGATION` |
| 真实任务 | 教师打开「初二（3）班」完成期中调座（查看名单→改规则→生成→确认→导出）；多班级教师日常切换；偶尔一次性排座 |
| 已知痛点 | 单页工作台（A）新手迷失下一步；步骤向导（B）老手用久繁琐；纯侧栏（C）对单次任务偏重 |
| 不可违反约束 | React 主流程完全绕过 Python（M2 §5.7）；导入/保存/迁移/编辑事务语义冻结于 Rust（§7.5）；v1.9.x 主流程不回退（§4.5） |
| 候选方案与 trade-off | A 单页工作台（直观、老手高效、迁移风险低）；B 步骤向导（引导强、线性事务对齐、老手繁琐）；C 侧栏工作区（多班级管理强、实现成本最高） |
| **最终决定** | **C 为骨架的融合方案**：左侧树形侧栏（我的班级 + 班级内容 + 临时工作台）+ 主区领域视图 + 顶部**上下文操作条**（按当前视图给出"下一步"建议，承载 B 的引导性）。**不做显式新手/老手模式开关**，采用上下文驱动 + 渐进披露（首次使用/无历史时显示任务清单，用过即收）。简单/复杂轮换按期数渐进披露（1 期=单次排座；多期=轮换计划）。临时工作台常驻侧栏（G-5） |
| 理由 | C 的生产力工具形态获认可；B 的引导性通过上下文操作条与首次任务清单获得，避免独立向导模式的重复维护；临时工作台覆盖"无需班级"场景并自然升级为班级 |
| 冻结阶段 | M4（交互契约草案）→ 目标形态页确认后冻结 → M5 实现 |
| schema/API 影响 | 无新 API；路由/状态模型需支持"班级上下文 + 临时工作台上下文"两种；临时工作台复用现有 import/solve/export 端点（不含项目写路径） |
| 待验证项 | 密度设置（紧凑/标准）是否保留；临时工作台与班级间的保存转换流程（dogfood） |

## D2 Seating canvas 交互

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D2-CANVAS` |
| 真实任务 | 教师对已生成方案做局部调整：挪 2–3 名学生、批量锁定/移动、精确指定座位 |
| 已知痛点 | 单拖拽（A）精确操作成本高；框选（B）触控/键盘不友好；表格（C）丧失空间感 |
| 不可违反约束 | §7.2 结果能力全项（定位/单选多选批量/状态可见/非法操作可识别/键盘核心操作）；持久编辑全部走 Rust editing 协议；undo/redo 不因视图切换破坏（G-2）；固定座位不可移动 |
| 候选方案与 trade-off | A 缩放+拖拽（直观、有成熟参照、触控实现成本高）；B 框选+批量（批量效率高、单座微调多一步）；C 表格直编（实现简单、键盘可达、空间感弱） |
| **最终决定** | **A 为核心的三视图并存**：画布主视图（缩放/平移 + 拖拽**整块跟随鼠标** + 框选批量 + 状态徽章）+ 表格视图（精确输入/批量属性/无障碍，同一编辑状态与 undo 栈，G-2）。视图切换按钮常驻工具栏 |
| 理由 | A 直观性获认可；拖拽整块跟随提升空间心智一致性；表格保留作为"UI 不便时"的兜底与无障碍路径 |
| 冻结阶段 | M4 → 目标形态页确认 → M5 实现 |
| schema/API 影响 | 无新 API；undo/redo 命令序列与现有 editing 协议一致；表格视图 = 同一 draft 的渲染投影 |
| 待验证项 | 触控支持是否 v2 必须（§7.2，由 Canvas Decision Gate 原型测试决定）；拖拽动效性能（60 座级） |

## D3 Rule builder

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D3-RULEBUILDER` |
| 真实任务 | 教师新增「学生丄004 与学生丌012 不要坐在一起（距离 ≥ 2）」；查看/调整现有固定座位与视力前排规则；复杂组合规则 |
| 已知痛点 | 纯句式（A）复杂组合表达受限；原"规则卡片"变体与句式区分度不足（评审指出的变体设计缺陷）；纯表单（C）新手感重 |
| 不可违反约束 | 规则参数 schema 唯一来源为 Rust RuleSpec/metadata（§7.3）；UI 不得自编译规则（M6 删除项）；未知学生/座位、字段缺失、明显冲突须即时发现；生成前可查看 feasibility summary |
| 候选方案与 trade-off | A 句式构建器（自然、槽位来自注册表、组合受限）；B 规则卡片（管理视图，被评审认为与 A 无本质区别——设计缺陷已记录）；C 分层表单（字段完整、渐进披露、表单感重） |
| **最终决定** | **句式构建器（创建入口）+ 规则卡片列表（管理视图）同屏融合**：卡片列表承载启用/停用、权重、排序、编辑、删除；新建规则用预置句式模板（学生距离/固定座位/标签分组/区域/成绩平衡/历史目标）；句式表达不了的组合规则经**"高级"按钮进入分层表单**（字段由 Rust registry 驱动） |
| 附决策 `PD-D3-ADJ-1` | **规则 JSON 禁止直接编辑，仅允许只读查看**（规则表示始终是 Rust RuleSpec 的产物，防止绕过校验）。如未来需要开放编辑，必须重新过 Decision Gate |
| 理由 | 创建与管理正交分层，消除原变体混淆；高级表单兜底保证可表达性（§7.3）；JSON 只读守住校验边界 |
| 冻结阶段 | M4 → 确认 → M5 实现 |
| schema/API 影响 | 无新 API；需要 Rust metadata 暴露"句式模板 → RuleSpec 参数槽"的映射；i18n 文案资产 |
| 待验证项 | 预置句式模板清单（与 Rust registry 对账）；高级表单的字段组织（dogfood） |

## D4 快速 vs 高级模式

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D4-QUICKADVANCED` |
| 真实任务 | 李老师「按班级现有规则再排一次，出 5 个方案挑一个」；王老师要精确控制种子/预算/权重 |
| 已知痛点 | 全展开（B）新手被 7+ 参数淹没；全隐藏则高级用户与复现性受损 |
| 不可违反约束 | §7.6 复现性：seed/solver/build/规则版本/history range/candidate id 可查可导出；默认隐藏 ≠ 不可见 |
| 候选方案与 trade-off | A 默认精简（3 问、默认值由产品冻结、高级用户需展开）；B 默认展开（复现零摩擦、与 CLI 语义一一对应、新手门槛高） |
| **最终决定** | **默认精简 + 高级设置不隐藏**：默认面板 3 问（规则集/候选数/本轮优先）+ **一行"历史：最近 3 期"（默认可见，不折叠——采纳评审保留意见：历史范围影响结果语义，属教师应见信息）**；种子/预算/去重/权重明细收进"高级设置"折叠区。默认值（candidates=5、历史 3 期）待 dogfood 冻结（G-4） |
| 理由 | 精简降低首次使用门槛；历史范围可见避免"为什么没避开上期同桌"的困惑；复现参数在折叠区仍可及（G-3） |
| 冻结阶段 | M4 → 确认 → M5 实现 |
| schema/API 影响 | 无；参数名与 Rust 契约一一对应（seed/time-limit/candidates/history-range） |
| 待验证项 | candidates=5 与历史 3 期默认值的真实任务验证 |

## D5 候选方案比较

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D5-CANDIDATES` |
| 真实任务 | 系统生成 5 个候选，教师回答：为什么推荐 A？A 与 B 差在哪？硬规则是否满足？座位分配差多少？ |
| 已知痛点 | 单视图各自残缺（表格缺空间感、雷达缺精确、差异高亮缺理由、逐规则信息过载）；**程序术语（fair_rotation 等）对教师不可读** |
| 不可违反约束 | 数据契约来自 Rust PlanScore（七维 + rule_scores + hard_constraint_summary）与 candidate distance（§7.7）；**复现信息可查（G-3）**；最终呈现以理解速度与误读率（可用性记录）为准 |
| 候选方案与 trade-off | A 对比表格（可扫描、差值着色、横向拥挤）；B 雷达图（形状直观、数值需二次操作、色弱不友好）；C 差异高亮（空间事实最具体、仅两两对比）；D 逐规则列表（最彻底、信息过载） |
| **最终决定** | **四视图融合，按教师问题组织（非拼图）**：① 推荐理由卡（2–3 句通俗话 + "硬性要求全部满足"徽章）；② 差异高亮（A vs 对比方案座位图 + 一行通俗差异）；③ 明细区（可切换：通俗分数明细 / 逐规则展开）；④ 雷达图为可选视图。**去术语化（G-1）**：术语映射表见下 |
| 术语映射表（程序 → 教师文案） | `fair_rotation`→轮换公平性（前后排机会均等）；`avoid_recent_neighbors`→避免和近期同桌/邻座再相邻；`score_balance`→成绩搭配（好带弱）；`height_back`→高个子靠后；`vision_front`→视力需求靠前；`diversity`→方案多样（几个方案差别够大）；`stability`→与上期变动幅度（平稳过渡）；`hard_constraint_summary`→硬性要求（全部满足 / N 项违反） |
| 理由 | 教师先要"结论与理由"，再要"空间差异"，最后才要"明细"；术语映射经 i18n 资产承载并可由 Rust audit message_key 驱动 |
| 冻结阶段 | M4 → 目标形态页确认 → M5 实现 |
| schema/API 影响 | 无新 API；需要 i18n 文案资产表（G-1）；推荐理由的生成规则需在 application 层定义（复用 audit 报告） |
| 待验证项 | 推荐理由卡文案模板；术语映射的可用性（误读率测试） |

## D6 可行性诊断

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D6-DIAGNOSTICS` |
| 真实任务 | 教师面对方案 C（2 项硬规则违反）：哪里错、为什么错、怎么改 |
| 已知痛点 | 列表（A）缺空间定位；向导（B）步骤冗长；内联（C）复杂问题放不下 |
| 不可违反约束 | 诊断数据来自 Rust audit（hard_constraint_summary + 七维 breakdown + missing_data + suggested_actions，§6.5）；修复动作走 Rust editing 命令 + 独立 validator 复核；不得硬编码 feasible=true |
| 候选方案与 trade-off | A 问题列表+高亮（全景+定位、需双向联动）；B 向导式修复（认知负担最低、步骤冗长）；C 内联诊断（所见即所得、复杂问题放不下） |
| **最终决定** | **A + C 融合**：画布内联徽章（红=硬规则违反 / 黄=建议）+ 侧边问题列表（严重级排序），**双向联动**（点列表高亮座位、点徽章定位列表项）；"一键修复全部"与逐条修复入口并存（走 Rust editing + validator）。B 的逐条引导不默认提供，违规较多时保留轻量"修复向导"入口（可选） |
| 理由 | 全景与空间定位并行；内联徽章与 D2 画布复用同一渲染组件（G-2 同源）；数据契约与 D5 共用 audit 报告 |
| 冻结阶段 | M4 → 确认 → M5 实现 |
| schema/API 影响 | 无新 API；与 D5 共用 audit 消费组件 |
| 待验证项 | 徽章密度在 60 人教室的可读性；"修复向导"入口是否保留（dogfood） |

## D7 历史 / 轮换模型

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D7-HISTORYROTATION` |
| 真实任务 | 教师回答"上期谁坐谁旁边""这期为什么这样轮换"；把 4 期轮换一起生成、批量保存 |
| 已知痛点 | 时间线（A）缺未来规划；版本（B）弱化轮换概念；周期计划（C）历史叙事弱 |
| 不可违反约束 | 轮换由 Rust 生成（每期独立求解、seed 逐期推进、历史快照参与评分）；批量轮换可批量保存/导出（§7.4）；快照文件（v1.x）持续可读；**快照恢复能力不可移除（数据安全）** |
| 候选方案与 trade-off | A 时间线（叙事自然、缺并排对比）；B 版本列表（操作语义清晰、弱化轮换）；C 周期计划（轮换一等公民、直接映射 Rust rotation 契约） |
| **最终决定** | **A + C 融合，双视图切换**：「历史回顾」= 时间线（节点点击回看该期方案，含"恢复此版本"入口——保留 B 的数据安全能力）；「轮换计划」= 多期卡片并排（逐期求解状态、批量保存/导出、生成下期）。两个视图切换不破坏编辑状态（G-2） |
| 理由 | 回顾（时间线）与规划（周期计划）是两种心智模型，双视图各自清晰；恢复能力以"恢复此版本"入口保留在时间线节点 |
| 冻结阶段 | M4 → 确认 → M5 实现 |
| schema/API 影响 | 无新 API；复用 rotation 产物（period_count/labels/base_seed/period_editors）与 snapshot 存储 |
| 待验证项 | 双视图切换对编辑状态的影响；"恢复"与当前编辑 draft 的交互语义 |

## D8 导入确认流程

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D8-IMPORT` |
| 真实任务 | 教师导入更新后的名单 CSV（20 行、2 行学号重复、1 列表头改名）：看清变化、处理冲突、原子生效、可回滚 |
| 已知痛点 | 向导（A）多次点击；单页（B）大文件单页过长；内联（C）弱化导入概念且新增学生场景低频 |
| 不可违反约束 | §7.5 事务语义（parse/apply 分离、apply 前预览、原子化、失败无半应用、可回滚、可审计）——**与 UX 无关、已冻结** |
| 候选方案与 trade-off | A 三步向导（与事务边界一致、步骤多）；B 单页预览（信息连续、步骤最少）；C 内联行级（与名单维护融合、弱化导入） |
| **最终决定** | **A + B 融合**：步骤条骨架（上传 → 映射预览 → 确认）+ 单页信息密度（映射编辑与冲突处理同屏、预览即时更新）；**不采用 C**（评审确认：新增学生概率不大，行级内联弱化导入不合理）。呈现形态与 D1 一致——导入是班级上下文内的引导面板，非独立全屏向导 |
| 理由 | 步骤条保留事务心智模型；同屏映射+预览减少往返；与 D1 导航一致性避免形态冲突 |
| 冻结阶段 | M4 → 确认 → M5 实现 |
| schema/API 影响 | 无新 API；事务语义维持 Rust application 层现状 |
| 待验证项 | 大文件（200 行）在单页预览的滚动体验 |
