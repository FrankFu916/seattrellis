## D9 导出面板分层

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D9-EXPORTPANEL` |
| 真实任务 | 期中调座后导出 PDF 发家长群、打印贴墙、做带隐私设置的名单表 |
| 不可违反约束 | 8 格式 + teacher/public 模板 + 6 隐私开关 + 页面参数已由 Rust export 实现并经独立 reader 验证（§5.6/§12）；产物经独立 validator 复核 |
| 候选与 trade-off | A 快速导出菜单（零摩擦、需默认值设计）；B 高级版式面板（参数全可见、日常繁琐） |
| **最终决定** | **A 快速导出菜单**：工具栏「导出 ▾」直接列格式，点击即用「上次设置」导出；「版式与隐私设置」入口收在菜单底部。**默认值设计是重点**——必须符合大多数人的需求，需要微调的用户走高级设置 |

| 待研究项 | **默认值矩阵具体取值**（格式 × 模板/隐私/页面）；「上次设置」记忆语义（建议全局记忆 + 班级可覆盖）；导出完成反馈形态 |

| 字段 | 内容 |
|---|---|

| schema/API 影响 | 无新 API；示例名单作为内嵌资产（Rust 或前端），标注"示例"并隔离 |
| 待研究项 | 示例名单的规模与内容设计（"恰到好处"的定义：建议 20–30 人、含常见属性）；任务卡的收起时机与「关闭引导」的持久化；与 D1 首次任务清单的关系（合并还是分层） |

|---|---|

| 真实任务 | 教师导出「打印 HTML」贴墙 |

| 待研究项 | **打印版式设计规范**（A4 分页规则、页眉含班级/日期/seed、页码、无交互元素、深色文字白底、字号层级）；print-html 与 html 的差异矩阵；独立 validator 结构验证 |

## D12 PDF CJK 字体（R 重新设计后冻结）

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D12-PDFCJK` |
| 真实任务 | PDF 座位表正确显示中文姓名 |
| 不可违反约束 | 安装包 5–20MB release gate；CJK 姓名必须可读；最小依赖政策（§5.6） |
| 候选与 trade-off | A 嵌入全字体（+10–15MB，触顶风险）；B 子集嵌入（体积优、实现最复杂 2–4 周）；C 系统字体 fallback（v1 缺陷：生成端检测不到字体就抹名） |
| **最终决定（R2，2026-08-12 实证修订）** | **导出端使用系统字体完成整页排版，以 144 DPI 无损页面图像封装进 PDF；不把字体解释委托给查看器。** 生成端继续按质量优先级枚举字体；不嵌入字体，不需要查看端安装同一字体。当前版本优先保证姓名在 Preview、Acrobat、Edge、手机等查看器一致可见；文字暂不可选中/搜索。若未来把“可搜索 PDF”列为核心需求，只允许实现字体子集嵌入，不再恢复字体名/GID 引用。 |
| 理由 | 原 R 方案的前提不成立：手写 PDF 把生成端字体的 GID 配合 `/Identity-H` 写入，却未嵌入该字体；查看器字体替换后 GID 不等价，实测 Poppler 出现 `Unknown character collection Adobe-UCS`，页面显示点、方框和错误拉丁字母。系统有字体不等于查看端能重建相同 glyph map。R2 在生成端一次性解析字体，以不可搜索的取舍换取跨查看器确定显示；这是用户反馈“PDF 只剩一堆点”后的 correctness-first 修订。 |
| 冻结阶段 | M4（方向冻结）→ 字体发现实现细节研究 → M5 实现 |
| schema/API 影响 | Rust 字体枚举/选择模块与 D13 PNG 共用；PDF writer 使用页面 Image XObject + lossless FlateDecode（编码失败回退 RunLengthDecode）；HTTP/DTO 不变。 |
| 待研究项 | 字体子集嵌入的体积/复杂度；无系统 CJK 字体时应显式失败还是提供安装指引；主要查看器视觉矩阵。 |

## D13 PNG 文字渲染

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D13-PNGTEXT` |
| 真实任务 | PNG 座位表发微信群，家长直接可读姓名 |
| 不可违反约束 | PNG 是位图；字体光栅化需新增 Rust 路径（建议纯 Rust 无依赖：fontdue/ttf-parser 类）；隐私开关对位图同样生效（public 匿名化 → 名字打码）；产物经独立 validator 复核 |
| 候选与 trade-off | A 渲染学生姓名（可读、需光栅化路径）；B 无文字（v1 现状，用途受限） |
| **最终决定** | **A 渲染学生姓名**（"座位表不能显示名字还有什么意义"——评审原话） |
| 理由 | PNG 是家长群最高频格式；无文字版本用途残缺 |
| 冻结阶段 | M4（方向冻结）→ M5 实现 |
| schema/API 影响 | Rust 新增文本光栅化（复用 D12 字体发现）；隐私过滤对位图生效（public 模板匿名化为「学生A/B/C」） |
| 待研究项 | 字号自适应与打码样式继续 dogfood；**2x 输出已于 2026-08-12 落地**；仍需积累 60 座级性能数据。 |

## D14 原生文件对话框（R 融合后冻结）

| 字段 | 内容 |
|---|---|
| decision_id | `PD-D14-FILEDIALOG` |
| 真实任务 | 选择本地 CSV 导入、选择导出保存位置 |
| 不可违反约束 | **安全红线（M1-05/io 可信根）**：任何文件读取路径不得绕过可信根与路径逃逸防御——手动输入路径只允许项目目录/可信根内相对路径，**禁止任意绝对路径**（Web 端经 loopback server 读取时尤其重要）；Web 工作台必须始终可用 |
| 候选与 trade-off | A Tauri 原生对话框（桌面体验好、双路径）；B 前端 input（单路径、无原生体验） |
| **最终决定（R）** | **三入口融合**：① 拖拽（所有端，HTML5 drag-drop）；② 系统对话框（桌面端 Tauri dialog API）；③ 手动路径输入（**仅可信根内相对路径**，带目录浏览联动）。Web 端拖拽 + input 兜底 |
| 理由 | 三入口覆盖不同习惯（拖拽/浏览/精确输入）；安全边界不因便利性放松 |
| 冻结阶段 | M4（方向冻结）→ M5 实现 |
| schema/API 影响 | Tauri dialog 插件依赖 + 权限清单；可信根内路径校验复用 io 层现有防御；能力探测驱动（桌面/Web 差异） |
| 待研究项 | 路径输入框的交互形态（自动补全/目录浏览联动）；E2E 中系统对话框的自动化策略 |
