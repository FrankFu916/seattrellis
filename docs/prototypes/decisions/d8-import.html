Decision D8 · 计划 §7.1 项 8 / §7.5

导入确认：三步向导 / 单页预览 / 内联确认

真实任务：李老师拿到更新后的班级名单 CSV（20 行，其中 2 行学号重复、1 列表头改名）。她需要安全地导入——看清每一处变化、处理冲突、确认后原子生效，随时可回滚。

数据正确性要求（§7.5，与 UX 无关、已冻结）：parse 与 apply 分离；映射/迁移/验证在 apply 前可预览；apply 原子化；任一步失败不得留下半应用状态；可安全回滚到导入前状态；导入产生的 schema/data 变换可审计。三个变体只改变呈现与操作顺序，事务语义完全相同（Rust application 层）。

单页把「映射 + 冲突 + 预览」同屏，适合对导入流程熟悉的教师。
优势一次滚动完成全部检查；映射与冲突上下文连续，改完立刻看到预览更新；步骤最少。
代价大文件（200 行）单页过长；新手容易被同屏信息分散；「确认」前缺少强制校验仪式感，误确认风险略高（有回滚兜底）。

行级操作（跳过/覆盖/合并）是预览阶段的选择，未提交前不影响现有名单；「提交全部更改」= 一次原子事务。
内联模式把「导入」变成「名单维护」的自然延伸；冲突处理下沉到行级。
优势与日常名单维护工作流融合（无需离开页面）；逐行决策粒度最细；对「增量更新」场景（每两周微调）最自然。
代价「导入」概念弱化，大文件全量替换时预览效率低；行级下拉/按钮多，视觉负担重；冲突处理规则（合并字段的语义）需要产品明确定义。
