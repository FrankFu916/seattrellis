Decision D3 · 计划 §7.3

Rule builder：句式构建器 / 规则卡片 / 分层表单

真实任务：教师想新增一条规则——「学生丄004 和学生丌012 最近闹矛盾，不要坐在一起（距离 ≥ 2）」；再确认现有「固定座位」与「前排优先（视力）」两条规则。普通教师不得被迫编辑 JSON。

可表达性（§7.3，全部变体必须满足）：常用 hard/soft 规则可创建/修改/删除；标签、区域、关系、距离、成绩/属性、历史目标可组合；规则参数 schema 的唯一来源是 Rust RuleSpec/metadata；UI 能立即发现未知学生/座位、字段缺失、明显冲突；生成前能查看 feasibility summary。
红线：React 不得自编译规则（M6 删除项），UI 只负责收集参数并提交 Rust 编译。

试一下：点击句中「选择学生…」槽位会弹出学生列表（本演示直接填入）；槽位填充完整后显示「可编译」。
优势零学习成本，句法与教师自然表达一致；槽位值全部来自 Rust 注册表，天然防止拼写错误；最适合「距离/关系/属性」类规则。
代价复杂组合（多条件 AND/OR、嵌套）超出句子表达能力时需退回卡片/表单；句式模板本身需要维护一套本地化文案。

优势一屏总览全部规则及启用状态；hard/soft 分层清楚；增删改查路径最短；与「规则卡片」心智匹配现有 React 卡片 UI，迁移平滑。
代价编辑复杂规则需弹窗/展开（多一层）；规则很多（10+）时列表变长；「拖拽排序」对触控不友好。
C
分层表单
主表单按「学生/位置/距离/历史」分组；规则类型选好后只显示相关字段（渐进披露）。
localhost:8765/class-302/rules/new
席序· 新建规则
参数 Schema 来自 Rust rule registry：{"rule":"min_distance","student_a":..,"student_b":..,"min":2}
校验：学生丄004 与学生丌012 均存在 · 距离值合法 · 与现有规则无冲突 → 可编译
表单按所选类型渐进披露字段；类型、性质、参数名全部来自 Rust metadata，UI 不重复定义规则语义。
优势字段完整、无歧义；最适合参数多的复杂规则；渐进披露避免信息过载；自动化测试最容易覆盖。
代价「表单感」较重，与教学场景的自然语言有距离；规则类型列表需要维护与本地化；新手仍可能选错类型。
