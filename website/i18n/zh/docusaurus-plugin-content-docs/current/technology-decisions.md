# 技术替代决策

评估日期：2026-10-01。所有技术都可以替换，但应以可测量的产品收益、平台要求或依赖失去支持为理由。数据生命周期的缺陷直接修复，因为更换语言或框架也可能复制相同错误。

## Rust、C/C++ 与求解算法

Rust 不是排座优化的数学必要条件。C++ 可以实现相同算法并直接接入 OR-Tools；C 适合紧凑 ABI，但需更多手动所有权管理与上层工具支持。同算法、同优化等级下，不能先验断言 C++ 比 Rust 更快。当前保留 Rust：它已负责校验、编辑、历史、隐私和导出，求解器生产依赖仅为 serde，重写全部行为需要重新证明等价性。原生 UI 可通过 C ABI 接入 Rust，不必重写核心。

SAT、CP-SAT、OR-Tools 与实现语言是不同层面的选择。OR-Tools CP-SAT 可用布尔/整数变量表达每人一座、固定位置、禁止配对及整数化目标。纯 SAT 还需要基数编码与 MaxSAT/伪布尔优化来表达加权目标。图距离、历史等须按现有语义编译；连续量整数化必须明确精度和溢出边界。“找到合法解”不能证明得到加权最优解。

已完成[新版可复现实验](https://github.com/FrankFu916/seattrellis/tree/main/benchmarks/solver-comparison/updated-2026-10-01)：使用优化后的 Rust 核心 `d8a7990` 与 OR-Tools 9.15.6755/已修补的 protobuf 6.33.5，保持九组 40/60/80 人输入、单线程、种子 42、两秒预算，每组运行三次。包含热启动建模和适配成本后，CP-SAT 在八组硬约束案例中更快；40 人混合案例则 Rust 更快（核心 64.4 ms、完整子进程 66.1 ms，CP-SAT 热流程 76.0 ms），60 人混合案例接近（196.3 对 183.9 ms）。两种引擎解出全部可行案例，并证明构造的不可行案例。36 份合法输出通过独立 Python 验证与 Rust CLI 审计；故意违反固定座位的负例也被两种验证器拒绝。

| 80 人案例 | Rust 核心中位耗时 | CP-SAT 热启动建模、求解与适配中位耗时 |
| --- | ---: | ---: |
| 简单 | 375.2 ms | 71.9 ms |
| 混合硬约束 | 403.3 ms | 330.3 ms |
| 已证明不可行 | 215.9 ms | 65.6 ms |

历史 OR-Tools 9.14 数据及对应 Rust 源码/二进制哈希单独保留。旧测量中 CP-SAT 九组均更快，但 Rust 分配优化后已不是当前结论。新结果仍支持开发可选 CP-SAT 后端，保留共享核心。实验比较算法与适配方式，不能证明语言速度排名：Python 适配器调用 OR-Tools 原生 C++ 引擎。单次 60 人冷进程耗时 529.5 ms，其中导入 OR-Tools 为 339.8 ms；该单次结果未计入热启动中位数。十项软目标全部关闭，CP-SAT 的加权质量、取消、多候选、轮换及原生打包尚未验证。生产后端须保持这些语义、七种状态和超时保留合法解的行为。继续保留 Rust 独立校验器和共享应用层，再完成这些对照。

## 技术栈逐项审查

| 当前技术 | 候选替代 | 决策与触发条件 |
| --- | --- | --- |
| Rust / Cargo / serde | C++ / CMake、C ABI、生成桥接 | 保留共享核心；按原生客户端需求增加桥接，有实测障碍再考虑重写。 |
| 自研约束搜索与局部搜索 | OR-Tools CP-SAT、SAT/MaxSAT、SCIP | 实测硬约束优势支持开发可选 CP-SAT 后端；生产采用前须验证软目标、生命周期与分发一致性。 |
| React 19 / TypeScript / Vite | Vue、Svelte、Solid、原生客户端 | 保留网页实现，按完整源数据、草稿版本及异步操作重构状态；换框架不能自动修复生命周期。 |
| 自建控件 | 无障碍 headless primitives、React Aria、设计系统 | 有选择地引入对话框、菜单、焦点工具；各原生端遵循官方规范。 |
| Tauri 2 / 系统 WebView | 原生 UI、Qt、Electron | 原生完整切片验收前保留当前产品；Electron 增加内置浏览器和包体成本，当前无已证明收益。 |
| Axum / Tokio loopback | FFI、UniFFI、WASM Worker、其他 HTTP 框架 | 保留有界桌面与浏览器传输；移动端优先进程内桥接，网页本地版使用 Worker。 |
| JSON / schemars / OpenAPI | Protobuf、FlatBuffers、CBOR | 保留可审查、版本化 JSON；测出载荷瓶颈才换二进制协议，协议与产品版本分别管理。 |
| 文件事务 / fs2 / SHA-256 ZIP | SQLite、平台文档 API | 现有规模保持可携文件；可搜索的持久历史可用 SQLite，迁移与原子导出必须先设计。 |
| 手写 CLI 参数解析 | clap、命令补全、稳定结构化输出 | 可渐进替换，保留命令名、退出码、dry-run 与输出路径契约；CLI 继续承担自动化入口。 |
| 自建 CSV/Excel 导入 | csv、calamine | 保持兼容，使用恶意形状、大文件、公式和现有导入契约测试成熟解析库后决定替换。 |
| SVG/HTML、Office XML 导出 | 成熟 OOXML 库、原生打印 | 本轮统一 XML 字符过滤并加入真实阅读器验收；支持库能降低维护且保持布局/隐私才切换。 |
| fontdue / ttf-parser / 系统字体 | skrifa、HarfBuzz/rustybuzz、矢量 PDF 库 | 评估字体维护与复杂文字 shaping；可检索和无障碍 PDF 需要真实文字层。 |
| 栅格 PDF | 矢量/文字、带标签 PDF | 后续产品能力，需验收字体嵌入许可、文字提取、屏幕阅读器和目标阅读器。 |
| Docusaurus / React / MDX | Astro/Starlight、MkDocs、VitePress | 保留双语静态站，修补依赖并对齐 Node 下限；构建成本与维护数据支持时再迁移。 |
| Vitest / Testing Library / Playwright | 浏览器组件测试、平台 UI 测试 | 保留 Web 回归工具，补原生无障碍与文档阅读器；输出快照一致不等于正确。 |
| GitHub Actions / cargo-deny / npm audit | 其他 CI、更多扫描器 | 保留，同一 ref 的质量门禁覆盖全部上传，固定编译器并检查版本；例外必须反映真实平台。 |
| Rust 1.88 下限 / Node 24 构建 / TS 分版本 | 新版受支持编译器 | 保留经过测试的下限与固定编译器，不盲目更新所有依赖；网页 TS7 与文档 TS6 有不同兼容限制。 |
| 静态文档与本地应用 | 托管后端、云同步 | 继续本地优先，WASM 是网页产品的首选实验；托管计算会改变学生数据的信任边界。 |

## 网页重构范围与版本

需要渐进式架构重构：完整班级源与编辑投影分开，每个草稿保留保存基线，任何源修改使旧请求失效，统一超时与取消，共享恢复/修复/导出用例。之后可将大型 App 拆为班级文件、生成与编辑 hooks，必须维持这些不变量及全程验收。整套换框架或建立空原生壳不能证明改进。

本评估不会把未验证的求解运行时、强制账号或新 UI 框架加入生产。源代码版本暂保持 2.1.0，发布时统一调整；真实保存/打开和 GUI 修复适合验收后的 2.2 功能版。公开文件、API、CLI 的破坏性变更决定是否升主版本，而不是使用哪种语言。
